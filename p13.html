A. Realistic Interview Prompt

"Design a search autocomplete / typeahead system — the kind of thing sitting behind the Google or Amazon search box — that suggests likely completions to a user as they type, ranked by how popular or relevant each completion actually is, and fast enough that it never feels like it's lagging behind the keyboard."

Every character a user types is, underneath, a fresh request for "rank and return the best few completions for this exact prefix," fired at keystroke speed, at a volume that dwarfs the number of searches actually submitted — a single search is preceded by several throwaway prefix requests that never turn into anything. The honest, load-bearing answer this problem is actually testing is one integrated decision: a Trie (prefix tree) with the top-K completions precomputed and cached at each node, rebuilt periodically offline from aggregated query logs, with a fast-moving "trending" overlay merged on top of that otherwise-stale structure, sharded by prefix range once the corpus outgrows one machine, and aggressively cached at the edge for the small set of short, extremely hot prefixes that account for a disproportionate share of all traffic.

B. Difficulty

Intermediate, growing into genuine distributed-systems territory in the deep dives — the read path itself (walk a tree, return a cached list) is conceptually simple once you know to reach for a trie at all; what makes this problem hard is everything around that read: keeping the structure fresh without paying a write cost on every keystroke (Patterns Playbook C), sharding a tree-shaped data structure rather than a flat keyspace (Patterns Playbook G), and layering personalization and typo-tolerance on top without breaking the one thing that makes the whole design fast — a shared, cacheable, precomputed structure.

C. What This Problem Tests

  • Recognizing that the naive, "obvious" implementation — a live database prefix scan, or an in-memory trie that recomputes ranking on every request — breaks specifically on the hottest, shortest prefixes, which is exactly backwards from what a scalable design needs
  • Precomputing expensive work off the hot path (Patterns Playbook C) as the central move, generalized here from "defer a side effect to a queue" to "defer an entire ranking computation to an offline batch job" — the same instinct behind News Feed's precomputed FeedEntry store (P3, Deep Dive O)
  • Sharding a data structure whose natural ownership boundary is a tree's own branches, not an entity ID — the same "shard by the natural ownership key" reasoning as Patterns Playbook G, just applied to prefix ranges instead of a row's primary key
  • Distinguishing a slow-changing, globally-shared bulk structure from a fast-moving, narrow "what's trending right now" overlay — two different freshness requirements that need two different mechanisms, not one compromise setting
  • Recognizing this as a read-heavy, staleness-tolerant system from the start (P11's caching reasoning applies almost unchanged) and being explicit about where personalization and fuzzy-matching can and can't be bolted onto a precomputed, shared cache without destroying its economics

D. Requirements

Functional

  1. Given a partial search string (a prefix), return a ranked list of the top-K most likely completions
  2. Ranking reflects overall popularity across all users — how often a completion has actually been searched — not simple alphabetical order
  3. Suggestions update, on some reasonable delay, to reflect genuinely new or newly-trending queries, not just what was popular when the system was first built
  4. Results are returned per keystroke, incrementally, as the user's prefix grows or shrinks
  5. (Extension, addressed in R/S) results can be personalized per user and tolerant of minor typos

Non-Functional

  • Very low latency — suggestions need to feel instantaneous relative to typing speed; a response arriving after the user has already typed the next character is functionally useless
  • Extremely read-heavy, at very high volume — every keystroke is a request, and only a small fraction of prefix requests ever culminate in an actual submitted search
  • Highly skewed traffic — a small number of short, common prefixes ("a", "how", "wea...") receive a wildly disproportionate share of total request volume relative to long, specific ones
  • Staleness-tolerant — a few minutes (or, for the bulk of the ranking, longer) of lag between "this query became popular" and "this query shows up in suggestions" is an acceptable, deliberate trade-off, not a correctness failure (elaborated fully in V)
  • Horizontally scalable storage — the full ranked corpus of query completions does not need to, and should not be assumed to, fit on one machine

Out of scope: full-text search over document contents (this system only autocompletes search-box query strings, not searching within results); a complete natural-language query-understanding layer; building a production-grade spelling-correction model from scratch (S names the mitigations available without claiming to design one in the room).

F. Assumptions

  • Confirmed: ranked, per-keystroke prefix completion, ranked by real popularity rather than alphabetically, with results that update over time as query trends shift.
  • Assumption: this is general, large-scale web-search autocomplete (E's clarifying question 5) — the assumption that makes sharding (P) and edge caching (Q) first-class parts of the design rather than something a smaller-scoped system would never need.
  • Assumption: both a slower, broad popularity ranking and a fast-moving trending signal are required (E's clarifying question 1) — treated throughout as two distinct mechanisms with two distinct freshness targets, never conflated into one setting.
  • Assumption: personalization (E's clarifying question 2) and typo tolerance (E's clarifying question 3) are both real, named extensions to the core design (R, S) rather than requirements the base trie itself must satisfy directly.
  • Assumption: the corpus of distinct query strings being ranked over is large enough (hundreds of millions of frequently-seen strings) that it will not comfortably fit in one machine's memory once precomputed rankings are included (E's clarifying question 4) — this is the assumption that makes sharding (P) load-bearing rather than a hypothetical extension.

I. API Design

-- client-facing:
GET /autocomplete?prefix={text}&limit=10          -> ranked list of { completion, score }
POST /events/click { user_id?, prefix, selected_completion }  -> fire-and-forget feedback signal (R, O)
-- internal, cluster-facing, not client-facing:
(query log stream) every submitted search -> durable log (Kafka, Prerequisites G)
(batch aggregation job) periodic: query log -> counts + decay weighting -> rebuild trie top-K caches (O)
(trending aggregator) continuous: recent window of query log -> TrendingDelta per prefix (O)
(shard push) new trie version -> blue-green deploy onto serving shards (O, P)

Why GET /autocomplete is the only latency-critical endpoint in the whole system: everything else — logging a query, aggregating counts, rebuilding the trie, recording a click — happens off the request path entirely, on its own schedule (Patterns Playbook C). The one endpoint a user is actually waiting on synchronously is the read, and every other deep dive in this problem exists specifically to keep that one read cheap.

J. Basic / Naive High-Level Design (V1)

The simplest thing that satisfies the functional requirement in isolation: on every keystroke, run a live query against the query-log database — SELECT query_text, popularity FROM queries WHERE query_text LIKE 'prefix%' ORDER BY popularity DESC LIMIT 10 — and return whatever comes back.

V1 — one live, sorted prefix scan against the database, recomputed from scratch on every single keystroke.

Why this breaks specifically on the traffic that matters most: for a long, specific prefix ("thermodynamics textbook re"), very few rows match, and the query is cheap regardless of how it's executed. But for exactly the short, common prefixes that make up a disproportionate share of real traffic (G) — "a", "th", "wea" — the LIKE 'prefix%' clause matches millions of rows, and the database has to scan and sort all of them, live, under a sub-100ms budget, on every one of thousands of concurrent keystrokes per second. The failure isn't a missing index — a leading, anchored prefix match can use one — the failure is recomputing an expensive rank-and-sort over an enormous, ever-growing candidate set from scratch, per request, for exactly the queries that arrive most often. An equally naive alternative — an in-memory trie with no precomputed ranking, which walks to the prefix node and then does a live DFS over its entire subtree to collect and sort every completion beneath it — has the identical flaw in a different shape: the subtree beneath a short, hot prefix is the largest subtree in the whole structure, so the traversal cost is again largest exactly where request volume is highest. Both point at the same fix: never rank live, at request time, over an unbounded candidate set — rank ahead of time, offline, and cache the small, already-sorted answer.

K. Data Model & Store Choice

The serving structure itself is a purpose-built, in-memory trie, not a general-purpose database: the access pattern is exclusively "walk down by character, read a small cached list at the end" — never a join, never a live aggregation — which is the same "match the store to the access pattern" reasoning from Prerequisites C and Distributed Cache's own storage choice (P11-K), just applied to a tree shape instead of a flat key space.

Raw query logs live in a high-write-throughput, append-only store (a durable log via Kafka, feeding into a wide-column or object store for the raw history) — this is by far the highest-volume write path in the system (billions of submitted searches, not counting the far larger keystroke volume that never reaches the log at all), and gets none of the read-optimized structure the trie has, because nothing ever queries it directly at request time.

Aggregated counts and the built trie version are the output of a batch job, stored as an immutable, versioned artifact (O) — pushed out to serving shards as a whole, rather than mutated in place, so a serving shard can swap to a new version atomically and cleanly roll back to the previous one if something's wrong with a rebuild.

Trending deltas and per-user history both live in Redis, TTL'd to their respective freshness window — both need fast, small, frequently-refreshed reads and writes, and both are inherently time-bounded, the same reasoning Notification System applies to its own short-lived digest batches (P12-K).

M. Deep Dive 1 — Trie Data Structure for Prefix Search

Requirement this addresses: sub-100ms lookups (D, G) regardless of how many completions share a given prefix — and directly fixes V1's core flaw (J), which got slower exactly where traffic was heaviest.

Why a trie beats a sorted-list binary search: binary search over a single globally sorted array of query strings gets you to the start of the matching range in O(log n) — but you still then have to scan forward through however many entries share that prefix to know what's there, and the array itself needs contiguous, shiftable storage that makes inserts expensive. A trie sidesteps both problems: each node represents one character position, with children keyed by the next character, so walking from the root to the node representing a given prefix costs exactly O(prefix length) — a small, fixed number (bounded by the longest reasonable query, generally under 20-30 characters) — regardless of how large the overall corpus is or how many completions live beneath that node. The lookup cost is decoupled entirely from corpus size, which a sorted-array scan's forward-scan step is not.

Why it beats a live LIKE 'prefix%' scan: the same reasoning V1's callout already covered — a B-tree index on the query text can get an RDBMS to the start of a matching range about as efficiently as a trie gets to a node, but ranking and limiting the result still requires touching and sorting every matching row, live, per request. A trie's advantage isn't really about finding the prefix — it's that the node itself, once reached, can hold an already-ranked answer (N), which a raw index range scan has no equivalent way to do.

The memory cost of a naive trie, not fully addressed yet: a trie storing one node per character of every distinct query string, without any pruning, explodes in node count — a corpus of hundreds of millions of distinct strings (G) produces a proportionally enormous number of nodes, and a large fraction of that structure is long, rarely-visited tail branches (one-off typos, extremely specific long queries) that cost real memory to store and are almost never actually requested. This is exactly why the offline batch job (O) filters out low-frequency noise before building the served structure at all — the trie this system actually serves is built over the aggregated, filtered corpus, not the raw, unfiltered firehose of everything ever typed.

N. Deep Dive 2 — Precomputing Top-K at Each Trie Node

Requirement this addresses: the second half of V1's flaw (J) — reaching the right trie node quickly (M) is only half the problem; ranking whatever's beneath it still needs an answer.

Why a live subtree scan at request time is still broken, even with a trie: the naive move, once you have a trie, is to walk to the prefix's node and then DFS/BFS the entire subtree beneath it, collecting every completion, sorting by popularity, and taking the top K — live, on every request. This has the exact same shape of flaw as V1: the subtree beneath a short, common prefix ("a", "th") is the largest subtree in the entire structure, so this traversal is most expensive precisely for the requests that arrive most often, the same backwards-scaling problem in a new costume.

The fix: during the offline build (O), compute and cache the top-K completions — already fully sorted by score — directly at each node, not just at the leaves. A request is then answered by an O(prefix length) descent to the node, followed by an O(1) read of that node's small, pre-sorted list — no subtree traversal of any kind happens at request time, ever.

The cost, paid deliberately: the same popular completion ends up duplicated in the cached top-K list of every one of its ancestor nodes — "new york pizza" appears in the stored list for "n", "ne", "new", "new ", and so on. This is a direct trade of memory for read speed, the identical denormalize-for-reads move behind News Feed's precomputed FeedEntry store (P3-O), just applied to a tree's ancestor chain instead of a follower list.

The gap this creates: a node's cached top-K list is only as fresh as the last full rebuild — a query that starts spiking in popularity right now will not appear in any node's precomputed list until the next rebuild runs, which for a corpus this size is not instantaneous. This gap is exactly what O's real-time trending overlay exists to cover, deliberately, rather than trying to make the precomputed structure itself real-time.

O. Deep Dive 3 — Updating the Trie at Scale

Requirement this addresses: keeping the ranking reasonably fresh (D) without paying a write cost on the single hottest, most latency-sensitive path in the system.

Why real-time insert-per-query doesn't scale: the naive alternative to a periodic rebuild is to update the trie live — every submitted search walks from the root down to its own terminal node, bumping a counter at every ancestor along the way, and potentially re-sorting each of those ancestors' cached top-K lists (N) to reflect the new count. That's an O(query length) cascading write, fanning out to every ancestor node, triggered by the full query-submission volume (billions/day, G) — turning what should be a pure, cheap read path into a read path that also does a chain of writes on every request, which is precisely the coupling this whole design exists to avoid.

The offline batch pipeline, concretely: submitted queries stream into a durable, append-only log (Kafka, Prerequisites G); a periodic batch aggregation job (running hourly, or every few hours) counts query frequency over a rolling window, applies decay-weighting so recent activity counts more than stale activity, filters out low-frequency and long-tail noise (M), and rebuilds each affected node's top-K cache from that aggregated count. The new trie version is pushed out to serving shards as a whole and swapped in via a blue-green deploy — old version keeps serving until the new one is fully live, so a rebuild never produces a visible gap or inconsistency mid-swap.

The trending delta layer, filling the gap the batch job leaves open: a separate, much lighter-weight streaming aggregator tracks query counts over a short, recent window (minutes, not hours) — using a streaming framework or simply short-TTL'd Redis sorted sets keyed by prefix — and produces a small overlay of fast-rising completions per prefix. At read time (L), this overlay is merged alongside the stale-but-broad base trie result, so a genuinely breaking, fast-moving query can surface within minutes without ever making the underlying bulk structure itself real-time.

Why the staleness this accepts is fine, not a compromise: the base trie being minutes-to-hours behind the absolute latest activity costs nothing correctness-wise — the worst outcome is a slightly-less-optimal ranked suggestion, never a wrong answer a user could be harmed by. This trade-off is stated explicitly and generally in V.

P. Deep Dive 4 — Sharding the Trie

Requirement this addresses: the full corpus trie (G) doesn't fit comfortably in one machine's memory once node overhead and the top-K cache at every node is accounted for.

The fix — shard by prefix range, the tree's own natural ownership boundary: a top-level split by the first character (or first one to two characters) of the query assigns each shard server a whole subtree — one shard owns everything rooted under "a"–"f," another "g"–"m," and so on. This is the identical "shard by the boundary within which data is almost always accessed together" instinct named generally as Patterns Playbook Pattern 6, just applied to a tree's own structural branches instead of an entity ID like event_id or doc_id.

Routing, without needing a consistent-hashing ring at all: because the prefix characters themselves directly determine ownership — the first character alone tells you which shard to talk to — a thin routing layer, or even a small client-side static range map (mirroring Distributed Cache's client-resolves-shard approach, P11-I), can route a request without a full hash ring. The "key" here is structurally, not arbitrarily, distributed across the keyspace, so a simpler mechanism than consistent hashing suffices.

Rebalancing for uneven load: query volume is not evenly spread across the alphabet — some starting characters are searched far more often than others — so a naive equal split by letter produces uneven shard load. The fix is splitting further down the tree specifically for hot ranges (a heavily-searched letter gets its own dedicated shard, or even splits further into two-character prefixes, while several rarely-searched letters share one shard), decided from observed traffic statistics rather than assumed evenly at design time.

Q. Deep Dive 5 — Caching Hot Prefixes

Requirement this addresses: the extreme, structural skew toward short, common prefixes (D, G) — the same read fan-in shape as a viral post (P3-P) or a hot key in a distributed cache (P11-P), just triggered here by prefix length rather than by one specific piece of content.

Edge/CDN caching for the base ranking: the non-personalized response for a given (prefix, locale/region) is largely identical across huge numbers of users, and only changes as often as the underlying trie rebuilds (O) — minutes to hours. That makes it an unusually good fit for edge caching (Prerequisites H) with a short TTL matched to the trending-layer refresh interval: a request for "a" or "the" is, in the common case, served entirely from a nearby edge node and never reaches an origin trie shard at all.

A layered caching hierarchy, each layer catching what the one above it can't: edge/CDN (coarsest, longest-lived, region-shared) → a shared Redis or in-memory cache sitting in front of the origin trie shards for whatever does reach them (Prerequisites D; the same cache-aside layering Distributed Cache itself is built around, P11) → the trie shard itself, as the final source of truth. Each successive layer absorbs progressively more specific or less-cached traffic than the layer above it could serve.

Personalized and trending results deliberately bypass the edge layer: both vary per-user or refresh too frequently for a long-lived, shared edge cache to be worth the complexity — only the base, global ranking is ever edge-cached; the trending overlay (O) and personalization (R) are merged in fresh, at origin, after the cacheable base result has already been fetched.

R. Deep Dive 6 — Personalization

Requirement this addresses: blending a user's own search history with global popularity (D, E) without undermining the one thing that makes this design fast and cheap — a single, shared, precomputed structure.

Where personalization fits, and deliberately nowhere else: the base trie lookup (M, N) and the trending overlay (O) both stay entirely global and shareable exactly as designed. Personalization is applied as a final, per-request re-ranking step at the API/serving layer, never baked into the shared cached structure itself. A small, bounded, per-user history store (UserQueryHistory, H) — the user's own recent searches and clicks, keyed by user_id — is checked in parallel with the trie lookup; any of the user's own recent queries matching the current prefix are boosted toward the top or injected alongside the global top-K, and the two results are merged only after both have independently returned.

Why this ordering is the load-bearing decision, not an implementation detail: baking personalization directly into the trie — a separate per-user trie, say — would multiply G's already-substantial memory estimate by the number of users, which is obviously infeasible at any real scale. Keeping personalization as a thin overlay merged at read time preserves the one shared, cacheable base structure (which is what Q's edge caching actually depends on) while still letting an individual user's own signal genuinely matter.

Deliberately bounded scope: only a small, capped set of a user's most recent queries needs to be checked per request — not their entire lifetime history — keeping this lookup itself cheap and bounded, the same "keep the addition cheap enough not to threaten the fast path" discipline behind N's node-local top-K design.

S. Deep Dive 7 — Handling Typos / Fuzzy Matching

Requirement this addresses: real human typing includes real typos (D, E) — and an exact-prefix trie, by construction, only ever matches completions that literally begin with the exact characters typed so far; a single dropped or swapped letter ("pyton" for "python") walks the trie down a path with no useful completions beneath it at all.

Why the trie itself structurally cannot solve this: the entire reason a trie's lookup is fast (M) is that it only ever needs to follow the one exact path implied by the characters typed so far. Tolerating an edit distance of even one character means potentially considering many divergent paths at once — insertions, deletions, substitutions at every position — which defeats the O(prefix length) lookup cost that's the whole point of the structure in the first place. This isn't a missing feature to bolt on; it's a fundamentally different access pattern than what a trie is built for.

Lightweight mitigations, roughly in order of increasing cost:

  • Phonetic/normalized secondary keys (a Soundex- or metaphone-style encoding) — index common queries under a phonetic key alongside the exact-text trie, so a phonetically similar misspelling can still be routed to the correctly-spelled term's bucket; cheap to add, but coarse and language-specific.
  • A secondary fuzzy index over only the head of the popularity distribution — a small edit-distance-aware structure (a BK-tree, or an n-gram index) built over just the tens of thousands of most popular queries, not the full corpus; full fuzzy search over hundreds of millions of strings is expensive, but restricting it to the queries actually worth catching typos for keeps it tractable.
  • A cheap client-side correction pass before the request is even sent — a small, bundled dictionary of extremely common misspellings, correcting the obvious case before it ever reaches the trie at all.

Worth naming explicitly, not glossing over: none of these are a complete, general-purpose fuzzy-search solution — this is an area where the honest answer is "good enough, bounded-cost mitigation for the common case," not "solve typo tolerance perfectly," and saying so directly is a stronger interview answer than quietly overpromising.

What stays stable throughout: the small GET /autocomplete contract from I — every later refinement changes how the answer is computed, cached, or merged, never the basic shape of what a client asks for.

V. Consistency Model

This system is, unusually among the problems in this document, eventually consistent everywhere, with no narrow strong-consistency island at all — worth noticing as a genuine contrast to the more common shape named in Patterns Playbook J, where most designs default to eventual consistency but still carve out one small piece of state that must be strongly consistent (a seat's hold status, a leader lock). There is no equivalent here: nothing in this system is a scarce resource being contended over, and no single request's correctness depends on reading the absolute latest write. The base trie (N, O) can lag reality by minutes to hours; the trending overlay (O) lags by a smaller but still nonzero window; personalization (R) reads a user's own recent history, which itself may be a request or two behind the very latest click. In every one of these cases, the worst possible outcome of staleness is a suggestion list that's slightly less optimally ranked than it could be — never a lost booking, a double charge, or a duplicated message, the kinds of failures strong-consistency islands exist elsewhere in this document specifically to prevent. Because nothing here is actually correctness-critical in that sense, this design leans as far toward "stale but fast and cheap" as the read-heavy, staleness-tolerant requirement (D) allows, without ever needing to walk that trade-off back for a specific field.

W. Failure Scenarios

  • A trie shard becomes unavailable: the shard router (P) detects the failure via health checks and routes requests for that prefix range to a replica of the same shard; if no replica is available, the system degrades to returning fewer or no results for that specific prefix range rather than failing the whole request path.
  • A batch rebuild job fails partway through or produces a bad build: serving shards continue serving the last known-good trie version (O) — the blue-green swap only happens once a rebuild completes and validates successfully, so a broken rebuild simply never gets promoted, and the failure is visible to on-call rather than silently corrupting live results.
  • The real-time trending aggregator falls behind or goes down: the trending overlay (O) is simply empty or stale for that window; the base trie (N) continues serving fine on its own, so a trending-pipeline outage degrades freshness for fast-moving queries specifically, without affecting the majority of traffic at all.
  • The personalization service is down: the API merges the base and trending results without a personalization boost — every user sees the same shared, unpersonalized ranking, a graceful degradation rather than a failed request.
  • A single hot prefix's edge cache entry expires simultaneously across many edge nodes: the same thundering-herd shape named for Distributed Cache's hot-key problem (P11-Q) — mitigated the same way, via request coalescing at origin so only one in-flight fetch per prefix reaches the shared cache/trie shard while concurrent misses wait on it.
  • A malicious or buggy client hammers the same rare, expensive prefix directly, bypassing normal traffic patterns: the layered cache (Q) and standard per-client rate limiting (reused as a cross-cutting concern, Patterns Playbook K) bound the damage to that one client's own allotment, rather than letting it degrade the shared origin tier for everyone.

Z. Common Bad Designs

  • A live LIKE 'prefix%' database scan with a live ORDER BY on every keystroke. Scales worst on exactly the short, common prefixes that make up the majority of real traffic — the single most important mistake to avoid on this problem.
  • An in-memory trie with no precomputed ranking, doing a live subtree scan per request. Fixes the wrong half of the problem — finding the prefix fast doesn't help if ranking what's beneath it is still done live, and the subtree is largest exactly where traffic is heaviest.
  • Inserting and re-ranking on every submitted query, live, against the serving structure. Turns a pure read path into a read-plus-cascading-write path at full query volume — the single change most likely to sink an otherwise-correct design under real load.
  • One giant, unsharded trie assumed to fit on one machine regardless of corpus size. Works fine in a small-scale demo and falls over the moment the corpus estimate in G is taken seriously.
  • Baking personalization directly into the shared, cached structure. Multiplies memory cost by the number of users and destroys the one thing (a single shared, cacheable base result) that makes edge caching viable at all.
  • Ignoring staleness as a design constraint entirely, insisting every suggestion be perfectly real-time. Solves a problem this system doesn't actually have — the honest answer is that a few minutes of lag costs nothing here, and insisting otherwise adds real complexity for no real benefit.

AB. Interviewer Evaluation Rubric

  • Weak candidate: proposes a live database query or an unranked in-memory list with no precomputation at all, and has no answer for why a short, common prefix would behave any differently from a long, rare one under load.
  • Mid-level: correctly reaches for a trie and recognizes it needs precomputed ranking, but treats "rebuild the trie" as a hand-wave rather than a concrete pipeline, and hasn't considered what happens once the corpus no longer fits on one machine.
  • Senior: proactively separates the slow-changing bulk structure from a fast-moving trending overlay; reasons concretely about sharding by prefix range rather than defaulting to a generic consistent-hashing ring without asking whether the keyspace's structure already gives a simpler routing answer; is explicit that this system has no strong-consistency requirement anywhere and says why.
  • Staff+: raises the hot-prefix caching problem unprompted and connects it explicitly to the same shape as a hot key or viral content elsewhere; is honest about typo tolerance being a bounded, cost-conscious mitigation rather than a fully solved problem; reasons about where personalization can and can't be added without destroying the shared-cache economics the whole design depends on.

AC. Interview Simulation

Interviewer: Design an autocomplete/typeahead system for a search box — as the user types, suggest likely completions.
Candidate: The first thing I want to avoid is computing the ranked list live, on every keystroke — a query against the raw query log with a live sort is fine for a long, rare prefix, but for something short and common like "a" or "the," you'd be scanning and ranking millions of rows under a tight latency budget, on every one of thousands of concurrent requests per second. So the core idea is a trie, with the top-K completions precomputed and cached directly at each node, built ahead of time from aggregated query logs rather than computed per request.
Interviewer: How do you keep that precomputed data from going stale?
Candidate: I'd split that into two separate mechanisms with two different freshness targets. The bulk of the ranking comes from a periodic offline batch job — query logs get aggregated with some decay weighting so recent activity counts more, and the trie gets rebuilt and pushed out every hour or so. That's deliberately not real-time. On top of that, I'd run a lightweight streaming aggregator that tracks a short recent window — the last few minutes — and produces a small "trending" overlay per prefix. At read time, I merge the stale-but-broad base result with whatever's in that trending overlay, so a genuinely fast-moving query can surface within minutes without ever making the core structure itself real-time.
Interviewer: What happens once that trie is too big to fit on one machine?
Candidate: I'd shard it by prefix range — one server owns everything under "a" through "f," another "g" through "m," and so on. The nice thing here is that the shard key falls directly out of the data structure itself; you don't need a consistent-hashing ring, because the first character of the prefix already tells you exactly which shard to route to. The one wrinkle is that query volume isn't evenly spread across the alphabet, so I'd expect to split further on whichever ranges turn out to be hottest in practice, based on actual traffic, not assumed evenly upfront.
Interviewer: How would you personalize results without redoing all of that per user?
Candidate: I'd keep personalization completely separate from the shared trie. The base lookup and the trending overlay both stay global and cacheable exactly as they are — personalization is a small, bounded check against the user's own recent search history, done in parallel, and merged in at the very end. Baking it directly into the trie — a separate structure per user — would multiply the memory cost by the number of users, which doesn't work at scale. Keeping it as a thin overlay lets one user's own signal matter without touching the shared structure everyone else depends on.
