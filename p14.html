A. Realistic Interview Prompt

"Design a cloud file storage and sync system like Dropbox: a user drops a file into a local folder on their laptop, and it should show up — correctly, completely, and without wasting bandwidth re-sending the whole file — on their phone and every other device they own, even if one of those devices was offline when the edit happened."

The naive framing of this problem — "store files, sync them to other devices" — hides the one detail that actually makes it hard: files are often large, edits to them are usually small (a few paragraphs in a huge document, a handful of frames in a video project), and devices are not reliably connected at the same time. Re-sending an entire file for every tiny edit, from every device, is the honest failure mode this problem is built to test whether a candidate avoids. The load-bearing decision this design is built around is: split every file into content-defined chunks using a rolling hash, so an edit only changes the handful of chunks actually touched (surviving insertions and deletions, unlike naive fixed-size slicing); store those chunks in a global, content-addressable, deduplicating chunk store, separate from a small metadata service that tracks each file's version history as an ordered chunk list; detect concurrent edits across devices with per-device version vectors rather than a single always-online ordering authority; and — because arbitrary file content has no composable edit semantics the way text operations do — resolve genuine conflicts by keeping both versions as a "conflicted copy" instead of attempting to automatically merge them.

B. Difficulty

Advanced — every individual mechanism (chunking, a metadata/blob split, version vectors) is independently well-understood, but the problem is genuinely hard to get right end to end because it demands recognizing what does not transfer from adjacent problems: the OT/CRDT machinery that solves concurrent editing for Google Docs (P9) does not apply here, and a candidate who reaches for it anyway — without noticing why it doesn't apply — is the most common way this problem goes wrong at the senior level.

C. What This Problem Tests

  • Recognizing that "sync the file" actually means "sync only the bytes that changed," and reaching for content-defined chunking rather than fixed-size slicing or whole-file transfer as the mechanism that makes that possible
  • Applying the metadata/blob store split (Patterns Playbook D, Prerequisites I) a second time in this document with a twist: the "blob" here is itself further split into content-addressed chunks, which is what turns a metadata/blob split into a genuine deduplication mechanism rather than just a storage-cost optimization
  • Detecting concurrent modification without a single, continuously-available ordering authority — the opposite structural assumption from Google Docs's per-document coordinating server (P9, Deep Dive M) — because devices here are routinely and expectedly offline for hours or days, not just briefly disconnected
  • Real judgment on why two adjacent-looking "collaborative state" problems (Google Docs's text edits, Dropbox's file edits) demand two fundamentally different conflict-resolution strategies, tied concretely to whether the underlying edits are composable or not — not just naming "OT" and "conflicted copy" as two options to pick between arbitrarily
  • Treating offline editing as the normal case to design for from the start, not a rare edge case bolted on afterward, which reshapes the notification/sync path (S) and the conflict-detection mechanism (P) alike

D. Requirements

Functional

  1. A user can upload, edit, delete, and organize files inside one or more synced folders
  2. Edits made on one device propagate to all of that user's other devices, without requiring the entire file to be re-transferred for a small edit
  3. A device that was offline when an edit happened correctly catches up once it reconnects
  4. If two devices edit the same file while both are disconnected from each other, the system detects that conflict rather than silently discarding one side
  5. (Extension, addressed in AA) shared folders across multiple users follow the same underlying mechanics as multiple devices for one user

Non-Functional

  • Bandwidth-efficient sync — the cost of syncing an edit should scale with the size of the edit, not the size of the file it was made to
  • Storage-efficient at rest — identical content, whether from repeated versions of the same file or entirely unrelated files across different users, should not be stored as duplicate bytes
  • Offline-tolerant by default — a device with no network connection must still let the user keep working locally, with sync resuming automatically and correctly on reconnect
  • No silent data loss — a legitimate edit from any device must never simply vanish because it collided with another edit; the honest failure mode when two edits genuinely conflict is surfacing the conflict, never discarding a side
  • Durable — once a device is told an edit has synced, that content must survive individual machine failures in the storage layer

Out of scope: real-time, keystroke-level collaborative co-editing of a single document's contents (that is Google Docs's problem, P9, not this one); fine-grained sharing permissions and link-based public sharing; client-side end-to-end encryption key management.

F. Assumptions

  • Confirmed: multi-device sync of arbitrary files, offline-tolerant, with conflicts surfaced rather than silently dropped.
  • Assumption: files are arbitrary, opaque byte sequences to the sync layer (E's clarifying question 1) — the sync engine never assumes it understands a file's internal structure, which is the assumption that makes content-defined chunking (M) content-agnostic and rules out semantic/text-aware merging (Q) as a general solution.
  • Assumption: a typical user syncs across a handful of devices (laptop, phone, tablet), and genuinely concurrent edits to the same file from two of them, while real, are the minority case rather than the common one (E's clarifying question 2) — conflict handling (P, Q) is designed to be correct and safe in that minority case, not optimized as if it were the dominant traffic pattern.
  • Assumption: offline editing is routine, not exceptional (E's clarifying question 3) — a laptop closed overnight or a phone with no signal for a day are both normal operating conditions this design must handle gracefully, not degraded edge cases.
  • Assumption: deduplication is global, across all users, not just across a single user's own file versions (E's clarifying question 4) — this is what makes the chunk store's content-addressing genuinely valuable at scale, versus being a narrower per-user optimization.
  • Assumption: file sizes span from small documents to multi-gigabyte project/media files (E's clarifying question 5) — large files are treated as a first-class case throughout, not an afterthought.

Why chunk upload/download are separate endpoints from the metadata commit itself: the metadata service handling sync-check and commit only ever touches small JSON payloads — hashes, vectors, version IDs — while PUT/GET /chunks/{hash} carry the actual large byte payloads, and can be served through pre-signed, direct-to-blob-store URLs exactly the way Prerequisites I's pre-signed URL pattern keeps large transfers off the application tier in Video Streaming's upload pipeline (Prerequisites I). Keeping these paths separate is what lets the metadata service stay small, fast, and cheap to scale independently of raw chunk traffic (O).

Why sync-check exists as its own call rather than folding into commit: a device needs to know which chunk hashes the server has never seen before it uploads anything — uploading blindly and letting the server discard duplicates on arrival would still waste the exact bandwidth this whole design exists to save (N).

J. Basic / Naive High-Level Design (V1)

The simplest thing that satisfies the functional requirement in isolation: whenever a file changes on any device, upload the entire file as one object, overwriting whatever was previously stored; every other device periodically checks whether the file's timestamp changed and, if so, downloads the entire new file in full.

(polls for changes)"]) -- "GET whole file" --> API API -- "entire file bytes" --> B

V1 — every save re-transfers the entire file, in both directions, regardless of how small the actual edit was.

Why this breaks specifically as files get large or edits get frequent: a one-character edit to a 200-page document, or a single corrected frame in a 4GB video project file, re-uploads and re-downloads the entire object every single time — the sync cost is tied to file size, not edit size, which is exactly backwards for a system whose whole value proposition is "small edits sync quickly." Worse, this design stores and transfers duplicate bytes with no way to notice them: two devices with two near-identical copies of a large file, or two entirely unrelated users who happen to save the same installer or the same shared template, each pay the full storage and bandwidth cost independently, because nothing in this design has any concept of "have we already seen these exact bytes." The fix isn't a faster network or a bigger disk — it's never treating a file as one indivisible unit of transfer or storage in the first place.

K. Data Model & Store Choice

Two structurally different stores for two structurally different access patterns, the same split named generally in Patterns Playbook D and Prerequisites I: a metadata service holds File, FileVersion, Device, and ConflictedCopy records — small, structured, and needing transactional, conditional-write guarantees (the version-vector compare-and-swap at commit time, P, is a textbook instance of Patterns Playbook B's check-then-act race) — while a separate chunk store holds nothing but raw chunk bytes, keyed by content hash rather than an application-assigned ID.

Why the chunk store's key is a content hash, not a random ID — the detail that turns a blob split into deduplication: in every other metadata/blob split in this document (News Feed's media, Chat's attachments, Video Streaming's files, all in Prerequisites I), the blob key is an arbitrary, application-generated identifier — two identical images uploaded by two different users get two different keys and are stored twice. Here, the key is a hash of the content itself, so two identical chunks — whether from two versions of the same file, or two entirely unrelated files from two unrelated users — hash to the same key and are, by construction, the same stored object. Deduplication falls out of the storage layer's addressing scheme itself, not a separate lookup-and-skip step layered on top.

Sharding/routing the chunk store by chunk hash: because chunk hashes are already uniformly distributed, pseudo-random values, they land almost perfectly onto a consistent-hashing ring (Prerequisites J, generalized in Patterns Playbook L) with no further thought required about hot ranges the way Autocomplete's prefix-range sharding needed (P13-P) — an unusually clean case of the pattern.

Why chunk bytes never live inside the metadata database: the same reasoning as Prerequisites I generally — bloating the metadata store's rows with megabytes of binary content would slow every backup, replica, and query touching that store, for the majority of records where nobody actually needs the bytes right now.

M. Deep Dive 1 — Chunking Large Files

Requirement this addresses: bandwidth-efficient sync (D) — directly fixing V1's core flaw (J), where sync cost scaled with file size instead of edit size.

Fixed-size chunking, the first thing most candidates propose, and why it mostly fails: slice a file into consecutive N-byte blocks by absolute offset — simple, and it does let an edit near the end of a file re-sync only the chunks after it. But a single byte inserted or deleted anywhere before the end of the file shifts the absolute file offset of every byte after it, which shifts every chunk boundary after that point, which means every single chunk from the edit onward hashes completely differently — even though almost none of their actual content changed. One inserted character near the start of a large file can defeat deduplication for the entire rest of the file. This is the "boundary-shift problem," and it's the specific reason fixed-size chunking, despite sounding like the obvious first move, is not the real answer.

Content-defined chunking with a rolling hash — the fix, and the same core idea rsync's algorithm popularized (AD): instead of cutting at fixed byte offsets, slide a rolling checksum (a Rabin fingerprint or similar) across a small window of bytes, and place a chunk boundary wherever that checksum satisfies a chosen condition (for example, its low N bits are all zero) — a condition that depends only on the local content under the window, never on the byte's absolute position in the file. An insertion or deletion shifts the bytes around it, but every stretch of content before and after the edit still contains the exact same byte sequences it always did, so the rolling hash finds the exact same boundary points around those unchanged stretches — re-producing the identical chunk boundaries, and therefore the identical chunk hashes, for everything the edit didn't actually touch. Only the chunk(s) immediately containing the edit differ.

Chunk size as a tunable trade-off, not a fixed constant: a smaller target chunk size means an edit invalidates fewer, smaller chunks (finer-grained dedup and delta sync, N) but increases the number of chunks — and therefore the size of the manifest and the per-chunk metadata overhead — for every file. A larger target chunk size does the opposite. The chosen average (~4MB, G) is a middle point, and a production system would reasonably vary it by observed file type (smaller chunks for frequently-small-edited documents, larger chunks for media files edited in bulk).

N. Deep Dive 2 — Delta Sync & Chunk-Level Deduplication

Requirement this addresses: the second half of V1's flaw (J) — chunking (M) only produces the right boundaries; delta sync is what actually avoids re-transferring or re-storing content that hasn't changed.

Upload side: after re-chunking locally (M), a device computes the hash of every chunk and calls sync-check (I) to learn which of those hashes the server has never seen before. Only chunks the server doesn't already have get uploaded — a chunk the device already synced in a previous version, or a chunk that happens to be byte-identical to something any other user has ever uploaded, is never re-sent.

Why cross-user dedup, not just per-user version dedup, is the bigger win: because the chunk store's key is a content hash rather than a scoped, per-user identifier (K), a chunk is deduplicated against the entire global chunk store, not just against one user's own file history. Two unrelated users independently saving the same conference-recording file, the same installer, or the same widely-shared template physically store those bytes exactly once, referenced by two completely independent FileVersion manifests. This is the concrete mechanism behind G's dedup-ratio estimate, and it's a strictly larger benefit than per-user dedup alone would ever produce.

Download side, symmetric to upload: a device fetching a newer FileVersion manifest diffs it against its own last-synced manifest (or, for a brand-new device, against whatever it already happens to have cached locally from other files) and downloads only the chunks it's actually missing — reassembling the file locally from a mix of previously-cached and newly-fetched chunks.

Garbage collection, the necessary counterpart to dedup: because one physical chunk can be referenced by many different FileVersion manifests across many files and users, a chunk's bytes can only be safely reclaimed once nothing anywhere references it — tracked via the ref_count field (H), decremented whenever a FileVersion that referenced it is superseded or deleted, with a periodic sweep reclaiming any chunk whose count reaches zero. This is the same deferred-cleanup discipline as reference counting in any shared-object system, applied here to keep the chunk store from accumulating orphaned bytes indefinitely.

O. Deep Dive 3 — Metadata / Blob Store Split, and the Chunk Store as Its Own Layer

Requirement this addresses: storage-efficient, cheaply-scalable data layout (D) — formalizing K's store choice into the concrete pattern this design directly reuses.

This is Patterns Playbook D and Prerequisites I, applied here with one extra layer: the general pattern is "small, frequently-queried metadata in a database; large payload bytes in blob storage," used elsewhere in this document for News Feed's media, Chat's attachments, and Video Streaming's files (all cataloged in Patterns Playbook D). This problem's metadata service plays the identical role — a FileVersion row is small, structured, and holds only a list of chunk hashes, never the bytes themselves. What's different here is that the "blob" side of the split isn't one object per file — it's the chunk store (K, N), itself a single, shared, content-addressed space that every file's manifest draws from. A FileVersion doesn't own its bytes the way a Chat attachment owns its one blob; it merely references a subset of a shared pool, which is exactly what makes cross-file, cross-user dedup (N) possible in the first place — the same metadata/blob split pattern, made more powerful by changing what the blob-store key means.

Why this split matters even more here than in its other appearances: G's capacity table showed metadata's footprint (roughly a petabyte) sitting three orders of magnitude below the chunk store's footprint (exabytes) — an even starker size gap than News Feed or Chat see, because file content genuinely dwarfs a chunk-hash list the way a photo dwarfs a post's caption, but more so. That gap is precisely why the two stores are scaled, replicated, and operated as entirely independent systems: the metadata service can run on fast, transactional, moderately-sized storage while the chunk store runs on cheap, massively-horizontal object storage tuned purely for durable byte throughput.

Why the chunk store still isn't "just" Prerequisites I's blob storage unchanged: ordinary blob storage (S3-style) is addressed by an arbitrary key chosen by whoever's writing; the chunk store here is addressed by a hash of the content itself (K), which is the one modification that turns a generic blob store into a deduplicating one. Worth being explicit about this distinction in an interview — it's a small change to the addressing scheme with an outsized effect on the system's actual storage economics.

P. Deep Dive 4 — Multi-Device Sync & Conflict Detection

Requirement this addresses: detecting a genuine concurrent edit across devices (D) — without assuming any single device or server is continuously online to arbitrate order the moment it happens.

Version vectors, the mechanism: each FileVersion (H) carries a version vector — conceptually a map from device_id to a monotonically increasing counter representing how many times that specific device has committed an edit to this file. When Device A commits a new version, it increments its own entry in the vector it last saw and sends that as based_on_vector (I). The metadata service compares the incoming vector against the file's currently-stored vector: if the incoming vector is a strict descendant of the stored one (every entry is greater than or equal, and at least one is strictly greater, with no entry going backward) it's an ordinary sequential update. If neither vector is a descendant of the other — each has an entry the other lacks — the two edits happened concurrently, and the commit is rejected with a conflict (Q), rather than blindly accepted and overwriting the other side.

Why this is the opposite structural assumption from Google Docs's ordering mechanism, and why that's the correct call here: Google Docs assigns a single, server-issued monotonic revision number per document (P9-O), which works specifically because one always-online coordinating server sits in the loop for every single edit and can assign a strict, global order in real time. That assumption is simply false here — a laptop closed for a business trip, or a phone with no signal for a day, is normal, expected behavior (F), not a rare disconnection Google Docs's design tolerates as an exception (P9-Q). Version vectors are the mechanism built for exactly this: they let two devices that have never been simultaneously online determine, purely by comparing two vectors after the fact, whether their edits were concurrent — no live arbiter required at the moment either edit was made.

Why this detects a conflict without needing to inspect file content at all: the comparison is pure metadata — two small vectors — so detecting "these two edits collided" costs nothing proportional to file size, and happens at commit time, before any large chunk transfer is even attempted for the losing side.

Q. Deep Dive 5 — Conflict Resolution: Why a Conflicted Copy, Not an Automatic Merge

Requirement this addresses: the no-silent-data-loss NFR (D) — once P detects a genuine conflict, something has to happen to both sides that isn't "discard one."

The direct contrast with Google Docs (P9), stated explicitly: Google Docs resolves a conflict by merging it — operational transformation (P9-N) mathematically combines two concurrent text operations into one coherent document, because an "insert character X at position 10" operation has well-defined, composable semantics: given two such operations, there is a mechanical, correct way to transform one against the other and produce a single result nobody needs to review. A changed chunk carries no equivalent semantics. "Chunk 7's hash changed" says nothing about what changed inside it — whether a paragraph was added, a row was deleted from a spreadsheet, or a few bytes of a binary header were altered — and the sync layer, by design (F), never inspects file content closely enough to know. There is no general transformation function that takes two divergent versions of an arbitrary chunk and produces one correct merged chunk, because "correct" depends on semantics the sync layer deliberately doesn't have access to. Attempting to guess — interleaving bytes, or picking one side's chunk over the other — doesn't reconcile the conflict, it silently risks corrupting the file, which is a strictly worse outcome than admitting the conflict exists.

The fix — keep both, and let the human decide: whichever commit the metadata service accepts first (P) keeps the original file_id and path, and syncs out normally to every other device. The commit that lost the version-vector race is not discarded — it's materialized as a new ConflictedCopy record (H), written out at a derived path ("report (Jamie's conflicted copy, 2024-06-01).xlsx"), and synced down to every device just like any other new file. Nothing is lost; nothing is auto-merged; the two divergent versions simply become two separate, fully-preserved files, and reconciling the actual overlap becomes a manual decision made by a person looking at both, not a decision the system makes silently on their behalf.

Why this isn't a workaround or a lesser design than Google Docs's — it's the correct answer to a genuinely different data model: if the underlying content were guaranteed composable (structured text edits with known semantics), automatic merging would be strictly better and this design would be missing something by not doing it. But because file content here is arbitrary and opaque by design assumption (F), conflicted-copy resolution isn't a simplification of Google Docs's approach — it's the industry-wide answer every general-purpose file-sync product converges on for exactly this reason, independent of vendor.

R. Deep Dive 6 — Offline Edits Queued Locally, Synced on Reconnect

Requirement this addresses: the offline-tolerant NFR (D) — a device with no connectivity must keep working locally and catch up correctly later, treated as the normal case (F), not an exception.

Local-first editing, and a durable local write-ahead queue: a device re-chunks (M) and computes new manifests on every save regardless of network state, and continues serving the file to the user entirely from its own local chunk cache the whole time it's offline — there is no user-visible difference between "editing while connected" and "editing while disconnected" from the local client's point of view. Every pending chunk upload and the eventual commit intent are appended to a small, durable local queue (a write-ahead log on local disk, so an app crash or device reboot doesn't lose queued work), each entry tagged with a stable, client-generated operation ID — the same idempotency discipline named generally in Prerequisites O — so that a queue flush interrupted partway through and retried from the start never double-uploads a chunk or double-commits a version.

On reconnect: the client first flushes any queued chunk uploads (N), then replays its queued commit exactly as it would have sent it in real time, still carrying whatever vector it was originally based on (P). If that vector is still the file's current stored vector — nobody else edited the file in the meantime — the commit lands cleanly, no differently from an edit that was never delayed at all. If the stored vector has since moved forward because another device committed while this one was offline, the commit is rejected as concurrent, and resolved through Q's conflicted-copy path exactly as it would be for two devices editing milliseconds apart while both online.

Why offline editing isn't a separate mechanism, only a longer delay before the existing one runs: this deliberately mirrors how Google Docs's own offline deep dive (P9-Q) reuses its online conflict machinery for a longer gap rather than inventing a new algorithm — the parallel stops there, though: Docs replays queued operations through OT and gets one merged document regardless of how long the gap was; this design replays queued commits through version-vector comparison and gets either a clean update or a conflicted copy, precisely because of Q's contrast between the two data models. A long offline period here doesn't change the mechanism, just the odds that the vector has moved on by the time reconnection happens.

S. Deep Dive 7 — Notifying Other Devices of Changes

Requirement this addresses: timely propagation (D) of "something changed, go sync" to a user's other devices — without paying for a resource commitment that doesn't match how those devices actually spend most of their time.

V. Consistency Model

This system is eventually consistent and explicitly offline-tolerant, with conflicts surfaced rather than silently merged or silently discarded — a third distinct consistency shape worth naming precisely, alongside the two most common shapes named elsewhere in this document. It is not Ticketmaster's narrow strong-consistency island (Patterns Playbook J): there is no single scarce resource being contended for here — no seat, no leader lock — so there's nothing to reject outright the way an oversold seat purchase must be. It is also not Google Docs's strong eventual consistency (P9-V), where any two replicas that have seen the same operations are guaranteed to converge automatically to one identical state, regardless of arrival order. This design's version-vector compare-and-swap at commit time (P) is, mechanically, the same check-then-act race named in Patterns Playbook B — but where every other instance of that pattern in this document resolves a "losing" request by rejecting or blocking it, here the losing commit isn't rejected outright, it's forked into a conflicted copy (Q). Two replicas that genuinely raced do not silently converge to one shared state the way Docs's replicas do — they deliberately land on two distinct, both-preserved files, and a human closes the gap OT/CRDTs would have closed automatically. Every other consequence of eventual consistency here — a device that hasn't synced in days simply catching up once it reconnects (R), a notification arriving some seconds late (S) — costs nothing beyond delay; the one genuinely different case, a real concurrent edit, costs a visible fork rather than a silent loss, which is the entire point of choosing this shape over either of the other two.

W. Failure Scenarios

  • The metadata service is unavailable during a commit attempt: the device's edit is already sitting safely in its local offline queue (R) regardless of server availability — the commit simply retries once the service recovers, with no data at risk in the meantime, the same graceful degradation offline editing already has to handle as its normal case.
  • A chunk store shard becomes unavailable: devices whose manifests reference chunks on that shard see a partially-synced file (missing just those chunks) rather than a failed sync entirely — chunk bytes are replicated across multiple storage nodes/AZs as baseline durability, so a single shard's temporary unavailability, not permanent data loss, is the expected failure mode; sync completes once the shard (or its replica) recovers.
  • Two devices commit concurrently to the same file: this is the case the entire version-vector/conflicted-copy design exists for (P, Q) — not really a failure so much as the expected, correctly-handled outcome; both edits survive, as two separate files, and nothing is silently lost.
  • A device crashes mid-chunk-upload: a partially-uploaded chunk is never referenced by any committed FileVersion manifest, so it's simply inert, orphaned data cleaned up by the ref-count GC sweep (N) — on restart, the device's durable local queue (R) resumes the upload from wherever it left off, using its stable operation ID to avoid any duplicate effect.
  • A chunk is unrecoverable due to a rare storage failure, despite replication: the specific FileVersion referencing that chunk is flagged corrupted, and the affected device falls back to the most recent version whose full chunk set is verified present, rather than silently serving a file with a missing piece.
  • The change-notification service is down: other devices simply don't get a timely "go sync" nudge — no state is lost, discovery of "something changed" just degrades to whatever periodic fallback interval a device falls back to once its long-poll connection fails, the same soft-degradation shape as Autocomplete's trending-overlay outage (P13-W).

Z. Common Bad Designs

  • Uploading and downloading the entire file on every change. Ties bandwidth and storage cost to file size instead of edit size — the single most important mistake to avoid on this problem, and the one that looks fine in a small-file demo.
  • Fixed-size chunking, assumed sufficient for dedup. Looks like a real fix until a single insertion or deletion is tested, at which point it defeats dedup for the rest of the file.
  • Scoping deduplication to just one user's own files. Misses the larger, genuinely available win of global cross-user dedup, for no real benefit in exchange.
  • Reaching for operational transformation or a CRDT to "merge" conflicting file edits, because it worked for Google Docs. Arbitrary file bytes have no composable edit semantics — this is the single most common way a candidate who's studied Google Docs (P9) gets this specific problem wrong.
  • "Last commit wins, silently discard the other." The same silent-data-loss failure mode as Google Docs's own V1 (P9-J) — a legitimate edit vanishes with no warning, which is exactly what this design's no-silent-data-loss requirement (D) exists to prevent.
  • Assuming a single, continuously-online authority can sequence every device's edits in real time. A structurally false assumption once offline editing (F) is taken seriously — the entire reason version vectors (P), not a live sequence number, are the mechanism here.

AB. Interviewer Evaluation Rubric

  • Weak candidate: proposes re-uploading/re-downloading the whole file on every change, with no concept of chunking or deduplication, and has no answer for why a small edit to a large file should be treated differently from uploading it fresh.
  • Mid-level: reaches for chunking correctly but proposes fixed-size chunks without noticing the boundary-shift problem, and treats "detect a conflict" and "resolve a conflict" as the same step rather than two genuinely distinct mechanisms.
  • Senior: proactively reaches for content-defined chunking and explains why it survives insertions/deletions where fixed-size chunking doesn't; separates the metadata service from the chunk store cleanly; reasons concretely about version vectors as a way to detect concurrency without a live arbiter.
  • Staff+: is unprompted and explicit about why this problem can't reuse Google Docs's OT/CRDT merge — tying the reasoning to composability of the underlying edit model, not just naming both mechanisms — and connects the metadata/chunk split explicitly to the same pattern used elsewhere in the document while correctly identifying what's genuinely different about it here (content-addressed keys enabling dedup, not just a size split).

AC. Interview Simulation

Interviewer: Design a file storage and sync system like Dropbox — a file changes on one device, and it needs to show up correctly on the user's other devices.
Candidate: The naive version — re-upload the whole file on every save, and have other devices re-download the whole thing — falls apart the moment files get large or edits get frequent, because the sync cost scales with file size instead of edit size. So the core idea is to split every file into chunks and only sync the chunks that actually changed. The tricky part is how you chunk: if you slice by fixed-size byte offsets, a single inserted character shifts every chunk boundary after it, so basically nothing dedupes anymore. The fix is content-defined chunking — a rolling hash finds boundaries based on the actual bytes nearby, not the absolute offset, so an edit only invalidates the chunks it actually touches.
Interviewer: Once you have chunks, how does the actual sync work?
Candidate: Each file version is really just an ordered list of chunk hashes — a manifest. When a device saves, it re-chunks locally, computes hashes, and asks the server which of those hashes it's never seen before; only those get uploaded. And because the chunk store is addressed by a hash of the content itself, not an arbitrary ID, dedup happens automatically — even across two totally unrelated users who happen to save the same file. Downloading works the same way in reverse: a device diffs the new manifest against what it already has locally and only fetches what's missing.
Interviewer: What happens if two devices edit the same file while both are offline?
Candidate: That's the part I want to be careful about. I'd give each file a version vector — basically a counter per device — so the server can tell, just from comparing two vectors, whether one edit came strictly after the other, or whether they happened concurrently without either device knowing about the other's change. If it's concurrent, that's a real conflict.
Interviewer: How do you resolve that conflict? Doesn't Google Docs just merge concurrent edits automatically?
Candidate: It does, but that only works because a text edit — insert this character at this position — has well-defined semantics you can mathematically transform against another edit and get one correct combined result. A file's bytes don't have that property. I don't know what changed inside a chunk just because its hash is different — it could be anything, and guessing how to merge two versions risks silently corrupting the file, which is worse than not merging at all. So instead of merging, I'd keep both: the version that commits first keeps the original filename, and the other becomes a conflicted copy at a new path, synced down to every device as its own file. It's less elegant than a merge, but it's never wrong, and that's the right trade for content the system can't safely interpret.
Interviewer: How do other devices even find out something changed?
Candidate: I wouldn't assume every device holds a permanent connection the way a chat app does — most devices in this system are closed or backgrounded most of the time. Long-polling is a good default: a device holds one request open, the server responds when something changes, and the device immediately reopens another. For devices that are fully backgrounded, I'd lean on the platform's own push notification service instead of holding a connection open at all.
